1. The one-paragraph model#

A region is a name. That name is hashed into a 16-byte transport key. When a node sends a flood packet it may attach a transport code — a 16-bit HMAC of the packet's payload under that key. A repeater holds a table of region names it knows; on receiving a flood packet it recomputes the code for each region it is willing to flood and looks for a match. Match → forward. No match → drop.

Consequences that fall directly out of that design and matter for every downstream doc:

  • Regions are per-packet labels, not addresses. Nothing about the packet's content, destination, or routing changes. The code is derived from the payload, so it is different on every packet even within the same region.
  • A region is only as secret as its name. For public (#) regions the key is SHA256(name) — anyone who knows the name can produce and recognise valid codes. This is a traffic-management mechanism, not an access-control one.
  • Only repeaters/room-servers enforce anything. Client (companion) firmware never drops a packet for region reasons.
  • Only flood-routed packets are filtered. Direct-routed packets (packets that carry an explicit path) are never region-filtered.

  • MAX_REGION_ENTRIES defaults to 32 and is not overridden by any variant or build config in the tree.

  • next_id starts at 1 and only ever increases. Region IDs are node-local; they are never transmitted and mean nothing to other nodes.
  • home_id and default_id are IDs of entries in the same table (0 = unset).

2.3 TransportKey — src/helpers/TransportKeyStore.h:7#

struct TransportKey { uint8_t key[16]; };

A 16-byte key. isNull() is true when all 16 bytes are zero, and null is used throughout as "no scope / send unscoped".

2.4 TransportKeyStore — src/helpers/TransportKeyStore.h:16#

An in-RAM cache of up to MAX_TKS_ENTRIES = 16 (region_id, key) pairs. The class is written as a facade over a future hardware keystore; in this snapshot the persistent side is unimplemented:

  • loadKeysFor() — cache lookup only; // TODO: retrieve from difficult-to-copy keystore. Returns 0 on a cache miss.
  • saveKeysFor(), removeKeys(), clear() — all // TODO and return false (they do nothing but invalidate the cache).
  • putCache() has // TODO: evict oldest cache entry; once 16 entries are cached, further entries are silently not cached. This is a performance issue only — getAutoKeyFor() recomputes correctly on a miss.

Implication: private ($) regions are non-functional in this snapshot. See §3.2.

RegionMap::getTransportKeysFor() — RegionMap.cpp:173. The first character of the stored name selects the derivation:

key = first 16 bytes of SHA256(name_including_the_leading_'#')

3.1 Consequences of the # handling#

  • foo and #foo are the same region — same key, and findByName()/findByNamePrefix() strip a leading '#' from both the query and the stored name before comparing (RegionMap.cpp:210, :221, via skip_hash() at :57).
  • The hash input is the name with the #, so a network agreeing on the region "europe" derives SHA256("#europe") regardless of whether individual nodes stored it as europe or #europe. Interop is safe across that spelling difference.
  • Names are case-sensitive. strcmp is used for lookup and the raw bytes are hashed. #Europe and #europe are different regions with completely different keys. This is the single most common source of "my region doesn't work" and belongs in any user-facing doc.
  • All display and export paths print names via skip_hash(), so the # is stripped in region output, region list output, and the region-discovery reply. A user who types #europe will see europe echoed back.

3.2 Private ($) regions are inert in this snapshot#

getTransportKeysFor() routes $-prefixed names to _store->loadKeysFor(), which can only ever return keys that were previously placed in the RAM cache — and the only thing that populates the cache is getAutoKeyFor(), which is never called for $ names. saveKeysFor() returns false and stores nothing. There is also no CLI or companion-protocol command anywhere in the tree that supplies a key for a $ region.

Therefore, at commit 8b9bee3b:

  • getTransportKeysFor() on a $ region returns 0 keys.
  • In findMatch() that region can never match, so a $ region can never allow a packet through.
  • In sendFloodReply() the num > 0 guard fails and the reply is sent unscoped.

$ is scaffolding for a future hardware-backed keystore. Treat private regions as not-yet-implemented.

4. Transport codes#

4.1 Computation — TransportKeyStore.cpp:4#

uint16_t TransportKey::calcTransportCode(const mesh::Packet* packet) const {
  uint16_t code;
  SHA256 sha;
  sha.resetHMAC(key, 16);
  uint8_t type = packet->getPayloadType();
  sha.update(&type, 1);
  sha.update(packet->payload, packet->payload_len);
  sha.finalizeHMAC(key, 16, &code, 2);
  if (code == 0) code++;             // reserve 0x0000
  else if (code == 0xFFFF) code--;   // reserve 0xFFFF
  return code;
}
  • Input is payload_type_byte || payload. The path is deliberately not included, so the code stays valid as the packet is retransmitted and its path grows hop by hop. Every repeater along the way recomputes and gets the same answer.
  • Output is the first 2 bytes of the HMAC, written directly into a uint16_t and later memcpy'd to the wire — so the on-air byte order is the platform's native little-endian, i.e. HMAC byte 0 then HMAC byte 1.
  • 0x0000 and 0xFFFF are reserved and never produced. {0, 0} is used explicitly as a "match nothing" sentinel — see §7.4.

4.2 Statistical properties#

The code is 16 bits, so a packet from an unrelated region has a ~1 / 65534 chance of falsely matching any given region a repeater checks. A repeater with N* flood-allowed regions has roughly *N / 65534 false-accept probability per packet. At the 32-region ceiling that is ~1 in 2048 packets. This is a deliberate airtime/effectiveness trade-off, not a security boundary.

Forgery is trivial for public regions by design: the key is SHA256 of a publicly-shared name.

4.3 Wire format#

Route type lives in the low 2 bits of the packet header (Packet.h:8, :14):

ValueConstantTransport codes present?
0x00ROUTE_TYPE_TRANSPORT_FLOODyes (4 bytes)
0x01ROUTE_TYPE_FLOODno
0x02ROUTE_TYPE_DIRECTno
0x03ROUTE_TYPE_TRANSPORT_DIRECTyes (4 bytes)

Layout (Dispatcher.cpp:149 decode, Dispatcher.cpp:311 encode):

[header:1] [transport_codes:4 (only if route type 0x00 or 0x03)] [path_len:1] [path:...] [payload:...]
           └ transport_codes[0]:2 (LE) ┘ └ transport_codes[1]:2 (LE) ┘

Packet::getRawLength() (Packet.cpp:36) adds 4 bytes when hasTransportCodes(). Scoping a packet costs 4 bytes of airtime.

  • transport_codes[0] is the scope — the only one ever matched against.
  • transport_codes[1] is always written as 0 by every sender in the tree. Both scoped senders carry the comment codes[1] = 0; // REVISIT: set to 'home' Region, for sender/return region? (simple_repeater/MyMesh.cpp:982, companion_radio/MyMesh.cpp:495, simple_room_server/MyMesh.cpp:746). It is reserved for a future "reply-to region" mechanism and is not read by anything.

4.4 Transport codes are not part of the packet hash#

Packet::calculatePacketHash() (Packet.cpp:40) hashes payload_type || payload and, for TRACE only, path_len. Transport codes and route type are excluded.

That hash is what the duplicate-suppression table keys on. So a scoped copy and an unscoped copy of the same payload are the same packet to a repeater's dedup logic: whichever arrives first wins, and the second is dropped as a duplicate regardless of its scope. In mixed networks this makes the effective scope of a message a race.

There is no scoped variant of sendDirect(). Path-routed traffic is structurally unscopable.

5.2 The sendFloodScoped() wrapper#

Each role implements the same shape (companion_radio/MyMesh.cpp:489, simple_repeater/MyMesh.cpp:976, simple_room_server/MyMesh.cpp:740):

void sendFloodScoped(const TransportKey& scope, Packet* pkt, ...) {
  if (scope.isNull()) {
    sendFlood(pkt, ...);                       // unscoped, ROUTE_TYPE_FLOOD
  } else {
    uint16_t codes[2];
    codes[0] = scope.calcTransportCode(pkt);
    codes[1] = 0;
    sendFlood(pkt, codes, ...);                // ROUTE_TYPE_TRANSPORT_FLOOD
  }
}

A null key silently degrades to an unscoped send. There is no error path.

5.3 Companion (client) scope selection — companion_radio/MyMesh.cpp:500#

Three inputs, in priority order:

  1. send_unscoped (RAM, set by CMD_SET_FLOOD_SCOPE_KEY sub-command 1) → force plain ROUTE_TYPE_FLOOD.
  2. send_scope (RAM, 16-byte key set by CMD_SET_FLOOD_SCOPE_KEY sub-command 0) → per-send override, pushed by the app before the send.
  3. _prefs.default_scope_key (persisted, 16 bytes, alongside _prefs.default_scope_name[31]) → the default scope.

If all are unset/null, the send is unscoped.

Two important asymmetries:

  • Adverts ignore send_scope. CMD_SEND_SELF_ADVERT with the flood flag builds a TransportKey from _prefs.default_scope_key directly and calls sendFloodScoped(default_scope, ...) (companion_radio/MyMesh.cpp:1254-1258). The per-conversation override does not apply. Adverts are always in the default scope or unscoped.
  • Channels have no scope of their own. sendFloodScoped(const GroupChannel&, ...) (:512) is byte-identical to the contact version, carrying // TODO: have per-channel send_scope. Per-channel scope is a client-app-level concept implemented by pushing send_scope before each send, not a firmware feature.

send_scope and send_unscoped are not persisted — both are reset at construction (companion_radio/MyMesh.cpp:875-876) and lost on reboot. Only default_scope_name/default_scope_key survive, via NodePrefs (companion_radio/NodePrefs.h:38-39, serialized as defs_nm and defs_key).

5.4 Repeater / room-server / sensor scope selection#

Infrastructure nodes have a single TransportKey default_scope in RAM, resolved at begin() (simple_repeater/MyMesh.cpp:932-950, mirrored in room server :707 and sensor :751):

RegionEntry* r = region_map.getDefaultRegion();
if (r) {
  region_map.getTransportKeysFor(*r, &default_scope, 1);
} else {
#ifdef DEFAULT_FLOOD_SCOPE_NAME
  r = region_map.findByName(DEFAULT_FLOOD_SCOPE_NAME);
  if (r == NULL) { r = region_map.putRegion(DEFAULT_FLOOD_SCOPE_NAME, 0); if (r) r->flags = 0; }
  if (r) { region_map.setDefaultRegion(r); region_map.getTransportKeysFor(*r, &default_scope, 1); }
#endif
}

DEFAULT_FLOOD_SCOPE_NAME is a compile-time -D flag. It is referenced in four files but defined nowhere in this repository — no platformio.ini, no variant, no build script. It exists so that a regional/community firmware build can bake in a default scope. Stock builds from this tree have it undefined, so a fresh repeater has no default scope until an admin sets one.

It also only fires when there is no persisted default region, and it auto-creates the region with flags = 0 (flood allowed).

default_scope is used for the node's own outbound flood traffic: sendSelfAdvertisement(delay, flood=true) calls sendFloodScoped(default_scope, pkt, delay, _prefs.path_hash_mode + 1) (simple_repeater/MyMesh.cpp:1010-1021).

The sensor node keeps a RegionMap purely for this outbound-scope purpose and for the region CLI surface — it never calls findMatch() and does not repeat.

5.5 Reply scoping on infrastructure nodes — sendFloodReply()#

simple_repeater/MyMesh.cpp:413:

void MyMesh::sendFloodReply(Packet* packet, unsigned long delay, uint8_t path_hash_size) {
  if (recv_pkt_region && !recv_pkt_region->isWildcard()) {
    TransportKey scope;
    if (region_map.getTransportKeysFor(*recv_pkt_region, &scope, 1) > 0) {
      sendFloodScoped(scope, packet, delay, path_hash_size);
    } else {
      sendFlood(packet, delay, path_hash_size);     // un-scoped
    }
  } else {
    sendFlood(packet, delay, path_hash_size);       // un-scoped
  }
}

Repeaters and room servers reply in the scope the request arrived in. This is what stops an admin locking themselves out: if you reach the repeater in region X, its path-return / login response / CLI reply goes back in region X. If the request was unscoped or matched only the wildcard, the reply is unscoped. If the matched region is a $ region (no keys available), the reply is unscoped.

recv_pkt_region is set once per received packet in onRecvPacket() and consumed later in the same processing pass — see §6.1.

Companion firmware does not do this. filterRecvFloodPacket() (companion_radio/MyMesh.cpp:479) is a stub returning false, carrying the comment:

// REVISIT: try to determine which Region (from transport_codes[1]) that Sender is indicating
//    for replies/responses; if unknown, fallback to finding Region from transport_codes[0]

A companion replying to a flood-routed message (ACK + path-return, BaseChatMesh.cpp:252) calls sendFloodScoped(from, path, ...), which uses its own send_scope/default_scope — not the scope the incoming message arrived in. This asymmetry is the root cause of the cross-region DM problem in §12.

6. Receiving and enforcement#

Enforcement exists only in simple_repeater and simple_room_server. The two implementations are identical in logic.

6.1 Classifying a received packet#

simple_repeater/MyMesh.cpp:549 (room server :310):

DispatcherAction MyMesh::onRecvPacket(Packet* pkt) {
  if (pkt->getRouteType() == ROUTE_TYPE_TRANSPORT_FLOOD) {
    recv_pkt_region = region_map.findMatch(pkt, REGION_DENY_FLOOD);
  } else if (pkt->getRouteType() == ROUTE_TYPE_FLOOD) {
    recv_pkt_region = (region_map.getWildcard().flags & REGION_DENY_FLOOD)
                        ? NULL : &region_map.getWildcard();
  } else {
    recv_pkt_region = NULL;             // both DIRECT route types
  }
  return Mesh::onRecvPacket(pkt);
}

Read the three branches carefully — this is the whole enforcement model:

  • Scoped flood → search the table for a region that (a) does not have REGION_DENY_FLOOD set and (b) produces a matching code. NULL if none.
  • Unscoped flood → the wildcard region's flag governs it. region denyf * is what blocks legacy/unscoped traffic; region allowf * permits it.
  • Anything direct (ROUTE_TYPE_DIRECT and ROUTE_TYPE_TRANSPORT_DIRECT) → NULL, unconditionally. Note that even a packet carrying transport codes on a direct route is classified NULL — direct routing bypasses region classification entirely.

6.2 Matching — RegionMap::findMatch(), RegionMap.cpp:190#

RegionEntry* RegionMap::findMatch(Packet* packet, uint8_t mask) {
  for (int i = 0; i < num_regions; i++) {
    auto region = &regions[i];
    if ((region->flags & mask) == 0) {            // region permits this class of traffic
      TransportKey keys[4];
      int num = getTransportKeysFor(*region, keys, 4);
      for (int j = 0; j < num; j++) {
        if (packet->transport_codes[0] == keys[j].calcTransportCode(packet)) return region;
      }
    }
  }
  return NULL;
}

Notes:

  • It only ever compares transport_codes[0].
  • Denied regions are skipped before any hashing — the flag check gates the key derivation. A denied region cannot match, so a denied region and an unknown region are indistinguishable in outcome.
  • The wildcard is not in the regions[] array and is never considered by findMatch(). Scoped packets can only match named regions.
  • Iteration is linear over all entries, first match wins. Cost per received scoped flood packet is up to num_regions × (one cached SHA-256 lookup + one HMAC-SHA256 over the payload). At the 32-region ceiling with a 16-entry key cache, regions beyond the 16th recompute their SHA-256 on every packet.

6.3 The forwarding decision — allowPacketForward(), simple_repeater/MyMesh.cpp:426#

bool MyMesh::allowPacketForward(const Packet *packet) {

}

The region check is guarded by isRouteFlood(), which is ROUTE_TYPE_FLOOD || ROUTE_TYPE_TRANSPORT_FLOOD (Packet.h:64). Direct-routed packets are never dropped for region reasons. This is the single most important fact for explaining cross-region messaging.

7. Hierarchy — and what it does not do#

RegionEntry.parent builds a tree rooted at the wildcard. The tree is presentational and structural only.

Grep the tree: parent is read in exactly three places — printChildRegions() (tree rendering, RegionMap.cpp:287), removeRegion() (the "must remove children first" check, :264), and CommonCLI region get (to display the parent's name, CommonCLI.cpp:1030). Plus it is written by putRegion() and the region load / region def parsers.

Therefore:

7.1 There is no flag inheritance#

findMatch() never walks parent. Setting region allowf europe does not allow uk, even if uk's parent is europe. Every region's REGION_DENY_FLOOD bit is evaluated in isolation.

7.2 There is no key relationship between parent and child#

getTransportKeysFor() never consults parent. SHA256("#uk") has nothing to do with SHA256("#europe"). A packet scoped to europe carries only the europe code and will not match a repeater that knows only uk.

"Hierarchical regions" in practice means listing every level you want to accept. A repeater that should carry both is configured with both europe and uk flood-allowed, and a sender that wants both audiences must send two packets or pick one. Whatever visual nesting the CLI shows is a bookkeeping aid for the operator.

7.3 Structural rules that do exist#

  • removeRegion() refuses if any entry has this region as its parent (RegionMap.cpp:264) — remove leaves first.
  • putRegion() refuses if the resolved parent is the region itself (RegionMap.cpp:158). This is the only cycle check; longer cycles (A→B→A) are not detected and would make printChildRegions() recurse without termination.
  • region load supports at most 8 indent levels (load_stack[8], simple_repeater/MyMesh.h:98).

7.4 The {0,0} "send nowhere" idiom#

BaseChatMesh::shareContactZeroHop() (BaseChatMesh.cpp:539) re-broadcasts a stored advert with:

uint16_t codes[2];
codes[0] = codes[1] = 0;   // { 0, 0 } means 'send this nowhere'
sendZeroHop(packet, codes);

Because calcTransportCode() never returns 0x0000, code 0 cannot match any region. Combined with ROUTE_TYPE_TRANSPORT_DIRECT and path_len == 0, this reaches direct neighbours and is guaranteed not to be flooded onward.

8. Persistence#

8.1 The region file#

RegionMap::load() / save() — RegionMap.cpp:72 / :119. Default path /regions2 (an optional path argument exists but every caller passes NULL).

Header (10 bytes):

Loading stops cleanly at EOF (a 0-byte read on id), on a short/partial record, or at MAX_REGION_ENTRIES. next_id is repaired on load: any record with id >= next_id bumps next_id to id + 1.

The 128-byte pad per record is forward-compatible space; a full 32-region file is ~5.2 KB.

8.2 Changes are RAM-only until region save#

region allowf, denyf, put, remove, home, def, and load all mutate the in-RAM RegionMap and nothing else. Only region save writes /regions2 — and it also stamps _prefs.discovery_mod_timestamp with the current time and calls savePrefs() (CommonCLI.cpp:1006-1010), so the node reports itself as "modified" to CTL_TYPE_NODE_DISCOVER_REQ queries that pass a since filter (simple_repeater/MyMesh.cpp:786).

region default is the exception: it calls onDefaultRegionChanged() and saveRegions() immediately, described in-source as "persist in one atomic step" (CommonCLI.cpp:1053-1054, :1064-1065).

8.3 The companion stores a key, not a table#

Companion firmware persists only default_scope_name[31] and default_scope_key[16] in NodePrefs. It has no RegionMap, no region table, and no region CLI. The client app is responsible for knowing region names and computing/supplying the 16-byte key. A companion cannot derive a key from a name on its own.

9.1 Name lookup: exact vs prefix#

Two different lookups are used, and the difference is user-visible:

  • findByName() — exact strcmp after stripping # from both sides. Used by region remove and by the region load parser.
  • findByNamePrefix() — memcmp on the first strlen(prefix) bytes; a complete match anywhere in the table wins, otherwise the last partial match found wins (RegionMap.cpp:218). Used by region allowf, denyf, get, home, default, put's parent argument, and region def's jump target.

So region denyf eu will hit europe — and if both europe and eurasia exist it deterministically picks whichever is later in the table, with no warning. Prefix matching is convenient interactively and a footgun in scripts. region remove is the only mutation that demands the exact name.

Both return the wildcard for the literal string "*".

9.2 region load#

Interactive, line-oriented, and stateful across commands. startRegionsLoad() (simple_repeater/MyMesh.cpp:1118) sets region_load_active; while that flag is set, MyMesh::handleCommand() intercepts every subsequent line before any other parsing (:1170) and treats it as a region definition. A blank line commits.

Per-line parsing (:1177-1198):

char *np = command;
while (*np == ' ') np++;          // count leading spaces
int indent = np - command;
char *ep = np;
while (RegionMap::is_name_char(*ep)) ep++;
if (*ep) { *ep++ = 0; }
while (*ep && *ep != 'F') ep++;   // optional flood flag anywhere after the name
if (indent > 0 && indent < 8 && strlen(np) > 0) {
  auto parent = load_stack[indent - 1];
  auto old = region_map.findByName(np);
  auto nw = temp_map.putRegion(np, parent->id, old ? old->id : 0);   // carry over existing id
  if (nw) {
    nw->flags = old ? old->flags : (*ep == 'F' ? 0 : REGION_DENY_FLOOD);
    load_stack[indent] = nw;
  }
}

Behaviours worth documenting:

  • Indentation is one space per level, and level 0 is the wildcard. A line with no leading space has indent == 0, fails the indent > 0 test, and is silently ignored. Top-level regions need exactly one leading space. This matches the region output format, which prints the wildcard at column 0 and its children at column 1 — output of region is valid input to region load.
  • Max depth 7 (indent < 8).
  • Existing regions keep their flags. The F flag on the line is honoured only for names that do not already exist; for known names old->flags wins. To change a flag on an existing region, use allowf/denyf, not load.
  • Existing regions also keep their id, so the key cache stays coherent.
  • The build happens in a separate temp_map; the live map is untouched until the blank line commits with region_map = temp_map.
  • Every line produces an empty reply, so a remote admin sees nothing until the commit line.

Side effect of the commit, from resetFrom() + the implicit copy-assignment. temp_map.resetFrom(src) copies only next_id (RegionMap.h:52):

void resetFrom(const RegionMap& src) { num_regions = 0; next_id = src.next_id; }

temp_map is a default-constructed member, so its home_id, default_id, and wildcard.flags are all 0. The commit is a whole-object copy (RegionMap declares no operator=), so region load resets the home region to unset, the default scope region to unset, and the wildcard to flood-allowed. Additionally, onDefaultRegionChanged() is not called, so the RAM default_scope key still holds the old value until reboot. A region load cycle on a node that had region denyf * re-opens it to unscoped traffic on the next save+reboot.

9.3 region def#

Parsed before parseTextParts() mutates the buffer (CommonCLI.cpp:987) because it needs the raw line. A cursor starts at the wildcard; each space-separated token is:

  • name → putRegion(name, cursor->id), flags = 0, cursor moves to the new region.
  • name|jump or name,jump → same, then cursor moves to findByNamePrefix(jump). The jump target is not the parent of name; it is where the next token will attach. Unknown jump → Err - unknown jump: <j> and the command aborts, leaving everything created so far in place.

The reply is the resulting tree. Unlike region load, region def writes directly into the live map — there is no temp/commit, so a partial failure leaves partial state. It does not clear existing regions, and it does not touch home/default/wildcard.

Note , is not a valid name character but | is, so the | split can collide with a name that legitimately contains |; , is the safer separator.

9.4 Name character rules — RegionMap::is_name_char(), RegionMap.cpp:52#

return c == '-' || c == '$' || c == '#' || (c >= '0' && c <= '9') || c >= 'A';

That is: -, $, #, 0–9, and every byte ≥ 0x41. The last clause is broad — it admits A–Z, a–z, all UTF-8 multi-byte sequences (hence the comment "accept all alpha-num or accented characters"), and also [ \ ] ^ _ \ { | } ~`.

Rejected: space, !, ", %, &, ', (, ), *, +, ,, ., /, :, ;, <, =, >, ?, @.

putRegion() validates the whole name against this and returns NULL on any illegal character (RegionMap.cpp:150-154). Note * is rejected — the wildcard is reachable only through the special-cased lookups, never through putRegion().

Length: char name[31] written via StrHelper::strncpy(dest, src, 31), which copies while buf_sz > 1 then NUL-terminates — so 30 characters maximum, silently truncated beyond that. The companion's CMD_SET_DEFAULT_FLOOD_SCOPE independently enforces n > 0 && n < 31, i.e. the same 30-character ceiling.

Since names are case-sensitive and hashed verbatim, a community should agree on a canonical spelling. Lowercase-and-hyphens is a sound convention, but it is a convention, not something the firmware enforces.

9.5 Tree output format — printChildRegions(), RegionMap.cpp:287#

<indent spaces><name><'^' if home><' F' if flood-allowed>

Recursion starts at the wildcard with indent 0. So:

* F
 europe F
  uk^ F
  france
 asia

reads as: unscoped traffic allowed; europe and uk flood-allowed; uk is the home region; france and asia are denied. The # prefix is stripped on output. The default-scope region is not marked in this output — use region default to read it.

10. Region discovery over the air#

Clients learn a repeater's region names with an anonymous request, no login required.

ANON_REQ_TYPE_REGIONS = 0x01 (simple_repeater/MyMesh.cpp:55). Handled in onAnonDataRecv() at :577:

} else if (data[4] == ANON_REQ_TYPE_REGIONS && packet->isRouteDirect()) {
  reply_len = handleAnonRegionsReq(sender, timestamp, &data[5]);
}

isRouteDirect() is required — a flood-routed regions request is ignored. In practice the client sends it zero-hop to a repeater it can hear directly. This is deliberate: it means region discovery works even on a repeater that denies the wildcard, because direct routing is never region-filtered.

handleAnonRegionsReq() (:147):

  • Rate-limited by anon_limiter; returns 0 (no reply) when throttled.
  • Request body is {reply_path_len:1}{reply_path:…} — the client supplies the return path.
  • Reply body is {sender_timestamp:4}{repeater_now:4}{names…}, where names come from exportNamesTo(dest, len, REGION_DENY_FLOOD) — i.e. a comma-separated list of flood-allowed regions only, # stripped, including a literal * first if the wildcard is flood-allowed (RegionMap.cpp:318-327).
  • Names that will not fit in the remaining buffer are skipped individually, not truncated mid-name.

The two sibling anon requests are ANON_REQ_TYPE_OWNER = 0x02 and ANON_REQ_TYPE_BASIC = 0x03; both are likewise direct-only.

On the client side this is driven by CMD_SEND_ANON_REQ (57) with an arbitrary payload, which since FIRMWARE_VER_CODE 13 may target a public key that is not yet a contact (a temporary contact is auto-added with out_path_len = 0, i.e. zero-hop direct) — companion_radio/MyMesh.cpp:1546.

12. Worked example: DMs between users with no shared region#

This is the scenario that confuses people, and every piece of it is determined by facts already established above. Setup:

  • Alice — companion, default_scope = "alpha".
  • Bob — companion, default_scope = "beta".
  • R1 — repeater near Alice: alpha allowed, beta denied, * denied.
  • R2 — repeater near Bob: beta allowed, alpha denied, * denied.
  • RX — a repeater in the middle that allows both alpha and beta (and denies *).

12.1 Why an established DM keeps working across regions#

Once Alice's contact entry for Bob has out_path_len != OUT_PATH_UNKNOWN, BaseChatMesh::sendMessage() takes the direct branch (BaseChatMesh.cpp:449-455):

if (recipient.out_path_len == OUT_PATH_UNKNOWN) sendFloodScoped(recipient, pkt);
else sendDirect(pkt, recipient.out_path, recipient.out_path_len);

sendDirect() sets ROUTE_TYPE_DIRECT, which carries no transport codes. Every repeater on that path classifies it recv_pkt_region = NULL (§6.1, third branch) — but the region check in allowPacketForward() is gated on isRouteFlood(), so it never fires. The packet is forwarded on region-agnostic grounds.

So: regions never break an established DM. Not Alice→Bob, not Bob's ACK back along the reverse path, not a path-refresh, not a login to a repeater you already have a path to. If a DM used to work and stopped, regions are the wrong thing to look at.

12.2 Where it actually breaks: bootstrapping#

Everything before a path exists is flood-routed, and every flood-routed step is filtered. Three separate steps must each find a region-permitted route:

Step 1 — Alice needs Bob's advert. Bob's flood advert is scoped to Bob's default_scope = beta (§5.3: adverts use the default scope, never send_scope). R2 forwards it. R1 denies beta and drops it. Unless it reaches Alice via RX and then some repeater near Alice that allows beta, Alice never sees Bob as a contact. Contact exchange out-of-band (QR / contact share) sidesteps this entirely and is the usual fix.

Step 2 — Alice's first DM. With out_path_len == OUT_PATH_UNKNOWN, sendFloodScoped() uses send_scope if the app set one, else default_scope = alpha. R1 forwards it, RX forwards it. R2 denies alpha and drops it. Bob never receives the message. If the app can set send_scope to beta for this conversation, R1 now drops it instead — unless Alice can reach RX directly.

The message gets through only if there is a chain of repeaters from Alice to Bob that all allow the one region the packet is stamped with. This is the crux: a flood packet carries exactly one scope for its whole journey. There is no gateway, no translation, no re-stamping at a boundary. transport_codes[1] — which the comments earmark for a return/home region — is hard-coded to 0 everywhere.

Step 3 — Bob's reply. Suppose step 2 succeeded via an all-alpha chain. Bob's firmware ACKs with a path-return, and because the incoming packet was flood-routed it calls sendFloodScoped(from, path, TXT_ACK_DELAY) (BaseChatMesh.cpp:252). That resolves to Bob's own send_scope/default_scope = beta — not the alpha scope the request arrived in, because companion firmware's filterRecvFloodPacket() is a stub and the incoming scope is never recorded (§5.5). So the reply is stamped beta, R2 forwards it, and the alpha-only repeaters between Bob and Alice drop it.

Alice's message arrives; Alice's client shows no ACK and no path; Alice retries; each retry floods again. That failure signature — one-way delivery, no delivery confirmation — is the characteristic symptom of a region mismatch, and it is worth stating plainly in user-facing docs.

Contrast with a repeater or room server as the peer: those do reply in the request's scope (§5.5, sendFloodReply() + recv_pkt_region), so repeater logins and CLI sessions round-trip correctly across a region boundary in a way that companion-to-companion DMs currently do not.

12.3 What actually makes it work#

Derived from the mechanics above, in rough order of robustness:

  1. A shared region with continuous coverage. Both parties send in the same region and every repeater on the route allows it. This is what a regional "umbrella" region (a state or metro-wide region that all local repeaters allow) is for, and it is why the guidance to set the default scope to a large region rather than a narrow one is mechanically correct: the default scope is what adverts and first-contact DMs use.
  2. Both users' repeaters allow both regions. Since a repeater's table is a flat list of independently-flagged names (§7), adding alpha and beta to both R1 and R2 costs nothing but two entries and makes both directions work. This — not nesting — is how overlapping coverage is actually built.
  3. Allow the wildcard (region allowf *), optionally with a low flood.max.unscoped so unscoped traffic stays local. Unscoped floods pass any repeater whose wildcard is flood-allowed, so a network with wildcard-allowed repeaters degrades gracefully to pre-region behaviour.
  4. Get a path established by any means, then it's direct forever (§12.1). Zero-hop contact sharing (shareContactZeroHop(), §7.4) and out-of-band contact import both bypass flood entirely.

12.4 The trap: a non-default default scope on infrastructure#

A repeater's region default sets the scope of its own outbound floods — principally its self-adverts (§5.4). If an operator sets region default private-thing on a repeater whose neighbours do not allow private-thing, that repeater's flood adverts propagate nowhere. The repeater still forwards other people's traffic correctly and still answers direct requests, so it looks healthy from its own console while being invisible to anyone who has not already got a path to it. Symptom: "my repeater works but nobody discovers it."

The mirror image on the companion side: setting an app's default scope to a narrow region makes the user undiscoverable, because their adverts go out in that narrow scope regardless of any per-conversation override.

Security properties

  • Public region keys are SHA256 of a shared name → anyone who knows the name can forge, recognise, and strip a scope. Regions are traffic management, not access control, and no user-facing doc should imply otherwise.
  • Scoping leaks nothing about payload contents (payload encryption is orthogonal), but the 16-bit code is a per-region-per-payload identifier: an observer who knows the region name can confirm that a given packet belongs to it.
  • Private ($) regions, which would have addressed this, are unimplemented (§3.2).
  • region commands over the air require admin authentication; over serial they do not.

Gotchas, consolidated

  1. Region names are case-sensitive and hashed verbatim.
  2. No flag or key inheritance through the hierarchy — the tree is cosmetic (§7).
  3. region load resets home, default scope, and the wildcard flag (§9.2).
  4. region load lines with zero indentation are silently ignored; top-level regions need one leading space.
  5. region load preserves the flags of existing regions, ignoring the F on the line.
  6. region default * resolves the wildcard, whose id is 0, and getDefaultRegion() treats default_id == 0 as unset — so it silently clears the default scope rather than setting it.
  7. allowf/denyf/get/home/default/put-parent use prefix matching; remove and the load parser do not.
  8. region put and region def create regions flood-allowed, while RegionMap::putRegion() internally defaults to deny — the CLI overrides it right after. A region created by any other path would be deny-by-default.
  9. Transport codes are excluded from the packet hash, so scoped and unscoped copies of one payload dedupe against each other (§4.4).
  10. transport_codes[1] is always 0; there is no return-region mechanism yet.
  11. REGION_DENY_DIRECT (0x02) is defined but never read.
  12. Changes need region save; only region default saves itself.
  13. A companion's stored default-scope name and key are independent; nothing validates that they correspond.
  14. Setting send_scope via CMD_SET_FLOOD_SCOPE_KEY clears send_unscoped.
  15. send_scope/send_unscoped are RAM-only and lost on reboot; the app must re-push them.
  16. DEFAULT_FLOOD_SCOPE_NAME is a build flag not defined anywhere in this repo — stock builds have no baked-in default scope.
